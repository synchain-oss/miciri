# 手动开始时，自然念 30 秒，方向步的第一个方向也等“开始”（桥版本不变）

两处行为改动只在手动开始时生效。自动推进（宿主测试的探针）不变，时间轴与分析次数和改动之前相同。
所有改动都是追加，`BRIDGE_API_VERSION` 仍是 2。

| 改动 | 内容 |
|---|---|
| `thresholds.json` | 新增 `session.natural_read_s`（30 秒，`pending`）；`session.natural_min_voice_s` 从 8 秒改成 20 秒；`click.analysis_window_s` 的说明改为只管自动推进 |
| 位置步的自然念 | 手动开始时一段 `session.natural_read_s`，到时间自己结束；有声满 `session.natural_min_voice_s` 后 `canEnd` 为真。自动推进仍是一段 `click.analysis_window_s` |
| 方向步的第一个方向 | 手动开始时 `startStep` 之后 `waiting` 为真，`canEnd` 为假，收到的音频丢掉，等 `startPhase` 才开始收，和后面三个方向、确认的两遍一样；这时调 `endPhase` 回 `no-phase`。自动推进不变 |

Result 的字段与分析算法都没有变。

## 自然念为什么是 30 秒、为什么新加一个阈值

原来的一小段话几秒就念完，用户念完就停，自然话只有几秒，口水音的每分钟次数主要靠两张字表。现在段落加长，界面请用户念完从头再念，
到 30 秒自己结束。30 秒是工程起始值，没有实录依据：口水音按次数算，自然话多收一些，计数不那么容易被一两下左右。

没有直接改 `click.analysis_window_s`：它是口水音那一组的值，分析拿到多少就算多少，宿主测试的探针时间轴和端到端的时间表都用它。
手动开始时念多久是流程的事，所以放在 session 组，和 `session.room_max_s`、`session.soft_clap_max_s` 这些上限放在一起。

`natural_min_voice_s` 是 20 秒，约是 30 秒的 70%。照平常的语速念，停顿占三成左右，所以大多数人要念到快结束才够，或者不够。
到 30 秒有声还不够 20 秒时，这一段也照样结束，和其他段到上限一样，不重来：口水音按两张字表加上收到的这些自然话算。

## 方向步的第一个方向为什么也等“开始”

原来点完准备页的“开始”，第一个方向马上开始收，用户还在电脑前，来不及坐回去、摆好话筒。这一步现在在会话里等，
不另加一个“开始第一个方向”的按钮。这样第一个方向用的是后面三个方向和确认那一段同一张待开始卡，界面上也不多一种状态。
其余各步的第一段照旧随 `startStep` 开始：增益、安静这两步本来就要人在话筒前；房间拍手和轻拍一直听，凑够才算，
从电脑前走回去的时间不碍事；重测走同一套脚本。

## 只改界面的几处（契约字段的含义不变）

- 房间拍手、轻拍：大字是“有效 n / 总数”，不倒数秒。差一下就自动结束时，主句说“再拍一下就自动结束”（房间）或“再拍一下就自动继续”（轻拍）；
  这时如果 `canEnd` 为真，下面加一行“拍不出来也可以现在点‘结束’”。这一条取代 `20261128-soft-taps-count.md` 里“进行中只写有效 n / 总数”的写法。
  其余按时间结束的段仍倒数，够了时说“够了”。
- 方向的叫法：按话筒哪一面朝你，开始时朝你的一面算正面，之后每次沿同一个方向再转四分之一圈，依次是侧面、背面、另一侧朝你，不写累计角度。
  雷达图、卡和详情用同一套叫法。
- 方向卡的数总是正的。当前方向最响时，是它比其他方向里最响的还响多少（`bestOtherAdvantageDb` 取反）；别的方向更响时，写是哪一面朝你时更响、
  响多少（那一面取 `repeatIndex`，没有时取 `levelDb` 里最响的另一个）。“可能放反了”用 `confirmedAdvantageDb`，其余用 `bestOtherAdvantageDb`：
  重测没确认时 `confirmedAdvantageDb` 是 0，原来卡上会写 0。报告里“上次 → 现在”只在两次的数意思相同（都是当前最响，或都是同一面更响）时才比。
